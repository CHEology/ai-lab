# AI Lab 文字排版与引用规范

状态：现行规范。制定于 2026-09-08。适用于在本仓库撰写、修改、生成和发布文字页面的 agent、AI 与人工编辑。

依据：作者确认的《爱世界的人，也有权说冷》引用改版。参考实现为 [文章源码](../writing/bodies/爱世界的人，也有权说冷.md)、[Markdown 构建器](../scripts/markdown.mjs)和[共享样式](../site/assets/style.css)。示例文章的观点不是所有文章必须采用的写作立场；引用数量也不是模板配额。

## 1. 入口、范围与权威

- 根目录 [AGENTS.md](../AGENTS.md) 是 agent 的执行入口，要求处理文字、引用、阅读页模板或样式前先读本文件。
- 根目录 [README.md](../README.md) 为人工编辑和新进入仓库的 AI 提供直接链接。[添加文字](ADDING-WRITING.md)负责操作流程。
- [DESIGN.md](DESIGN.md)负责全站标识、目录、配色和路由；本文件负责阅读页面的内容结构、文字排版、引用及注释交互。涉及两者的改动须同步更新，不维护互相矛盾的数值。
- 本文件是仓库维护文档，不列入作品目录，不生成读者页面，不在文章中添加“给 AI 的说明”、构建说明或规范入口。
- 适用于 `writing/` 及其模板。实验作品内部排版可以另定；Blue Note 的主题、正文和发布流程由其仓库管理。
- 用户当前明确指示优先于本文。用户要求保留特定排版、引文体例或仅做局部修订时，按当次范围执行，不把本规范当作扩写、重写或跨站修改的授权。

## 2. 编辑边界

1. 排版、引用调整默认保留文章的主张、措辞、段落顺序、独立标题、署名和首次发布日期。不得为了符合模板而改写个人表达。
2. 区分原文直接说了什么、本文如何解释，以及尚不能确认的事实。保留“我猜”“这是推测”等有效限定，不把人物台词或玩家评论改写成官方结论。
3. 发现疑似事实错误时先核对。不能确认就记录具体问题；不靠更换引文或删去限定语把疑问隐藏起来。
4. 署名来自作者提供的元数据。不得推测模型名称、版本、创作经历或人工编辑比例。纯排版修订不更新 `published` 冒充新作。
5. 不为短文硬添摘要、导语、小标题、结语、参考文献或 AI 声明。结构必须服务于实际内容。
6. 引用不自动授权大段复制。以必要短引与准确转述为主，避免把外部作品正文搬进注释。

## 3. 页面结构与元数据

从上到下采用以下顺序；可选部分没有内容就整体省略：

1. 小型 ai-lab 字标与所在目录，由模板生成。
2. 唯一的 H1；取 `responseTitle`，未指定时沿用现有生成规则。
3. 实际署名（若有）和首次发布日期，由元数据生成。
4. 可选文章目录：仅在作者允许且有至少两个主要章节时，通过 `toc: true` 启用。
5. 正文：连续段落，以及内容确实需要的 H2/H3、引文、图表或列表。
6. 注释：有注号时自动生成可见的“注释”H2和有序列表。
7. 延伸阅读：有额外推荐材料时用 `## 延伸阅读`，最终显示在注释之后。
8. Blue Note 原文入口：存在 `source` 元数据时由模板生成。

正文 Markdown 不写 H1，不重写署名、日期或底部导航。`title` 继续用于目录与固定 URL，`responseTitle` 仅用于阅读页与浏览器标题。不要因改标题、换引文体例而更换已发布路径。

`pending` 页仍只显示待写提示和原文入口，不生成空注释、虚构正文或署名；使用 `noindex, follow`。`draft` 不进入部署产物。

## 4. 正文排版

### 4.1 字体与尺寸

尺寸基于浏览器默认 16px；代码使用 rem/em，保留浏览器缩放和用户字体设置。所有阅读页共用 `site/assets/style.css`，不在单篇 Markdown 写内联 CSS。

| 元素 | 规范 |
| --- | --- |
| 阅读列 | 最大 `39.667rem`（约 635px），居中，窄屏由容器留边 |
| 正文 | `1.0625rem`（17px），行高 1.78，Charter / Georgia / 中文宋体回退 |
| 段落 | 段后 `1.15em`，不首行缩进；用段落间距区分，不堆空行 |
| H1 | 32px，行高 1.35，常规字重；640px 及以下约 25.6px |
| 正文 H2 / H3 | 22px / 18px，常规字重，行高 1.4；上距 2em，下距 1em |
| 署名与日期 | 13px，无衬线，辅助文字颜色 |
| 注释 / 延伸阅读 | 15px，行高 1.75；内容仍用阅读字体 |
| 附录标题 | 16px，无衬线，500 字重；避免和正文 H1 竞争 |
| 正文注号 | 约正文的 70%，无衬线，上标，不撑开正文行距 |
| 注释编号 | 13px，无衬线，辅助文字颜色 |

浅色与深色都使用全站色彩变量。正文、注释内容保留正文颜色；日期和辅助编号才使用 muted。不得为了“轻”把整段注释淡化到难以阅读。

### 4.2 段落、标题、标点与强调

- 保持左对齐，不强制两端对齐，不设置固定高度或裁切长文。长 URL、长单词可换行。
- 中文新稿使用全角中文标点、中文引号“”及内层‘’；书名用《》，文章标题可用〈〉。代码、作品固有名称、英文引语内部保留原来的拼写和标点。
- 新稿中中文与完整英文名称、数字之间通常留一个半角空格；旧稿仅在排版修订范围允许时统一，不批量改变专名、路径、数字格式或作者有意的写法。
- 不用连续空格、全角空格、`&nbsp;` 或重复 `<br>` 做布局。诗歌、地址等确有逐行意义的内容可以保留换行。
- H2/H3 用于真实的论述层次；不跳级，不用加粗段落假装标题，不为每个自然段起标题。
- 加粗用于少量确需定位的信息；不自动把每段首句或结论加粗。斜体可用于外文作品名或确有意义的强调，不把整段中文正文设斜体。
- 无序列表用于并列项目，有序列表用于顺序和步骤；散文与评论默认连续段落。不要把原文拆成问答、清单或卡片。

### 4.3 引文与其他内容

- 短引语留在句内。长引语使用 Markdown `>`，左侧细线与留白，不放装饰性大引号、阴影或卡片底色。
- 引语标明说话者或作品，并在相关句末落注。译文如为自译或据转译，准确注明；不擅自把转述改成直接引语。
- 图片需要有意义的替代文字；正文图片最大宽度 100%，等比缩放。图片来源按实际归属记录，不借图片注释新增未经授权的图片。
- 表格只用于对应关系或数据比较；代码块使用 fenced code，按实际语言标记。表格和代码块在自身范围横向滚动，不撑宽页面。
- 公式使用 `$B\propto M^{2/3}$` 行内语法；独立公式的起止 `$$` 各占一行。构建时由锁定版本的 KaTeX 输出原生 MathML，保留可读的分数、上下标与 TeX 语义注解；不使用截图、浏览器脚本、远程字体或 CDN。行内公式随正文字号，独立公式居中，仅在公式自身范围横向滚动并可键盘聚焦。公式两侧的 `$` 紧贴内容；字面美元符号写 `\$`，示例代码仍使用反引号。无效 TeX 构建失败，不把错误标记当成公式发布。新增复杂公式应在 Chromium 和 WebKit 中分别验收。
- 水平分隔线仅用于确实的内容分界。正文中的线采用 4rem 短线；注释区由样式自动提供阅读列宽度的分界线，作者不重复加 `---`。

### 4.4 可选文章目录

- 目录是单篇元数据 `toc: true` 的显式选择，默认不生成；当前《规律还不是操作说明》依据作者 2026-09-08 的许可启用。不得为其他旧稿批量添加。
- 入口位于日期之后、第一段之前，使用原生 `details/summary`，默认收起。入口文字仅为“目录”，辅以小折角与底部一条细线；不加卡片底色、摘要、阅读时长、浮动侧栏或悬浮按钮。
- 展开后只列主体 H2，按正文顺序一列排开；不把注释和延伸阅读混入主要论述。少于两个主要章节不显示目录。
- 目录用 14px 系统无衬线字体；展开入口至少 44px 高，链接有足够行间留白与清晰键盘焦点。点击使用普通锚点，目标标题留有顶部空隙，可接收焦点。
- H2 目标 ID 由标题生成，带 `section-` 前缀；重复标题追加后缀，片段 URL 按标准编码。修订已发布标题时检查既有片段地址的影响。目录正文由构建器生成，稿件不手写目录 HTML。

## 5. 何时引用、何处落注

### 5.1 需要引注的内容

直接引语、可核对的剧情与人物行动、历史/科学/技术事实、统计数据，以及借鉴他人的具体论点，应有可追溯依据。读者必须能区分引用所支持的事实与本文基于该事实做出的判断。

作者的感受、本文自己的比较与推理，不因“听起来重要”就需要外部链接。不要把整段评论后面的一条网址，当成该段每个结论都已被来源证明。

### 5.2 落注规则

- 默认在相关完整句的句号、问号或引语外层标点后放一个上标注号，紧贴标点，不加括号，不把网站名塞进句尾。
- 同一短段连续转述同一场景时，可以在转述结束处共用一注；注释中说明覆盖范围。不要跨过很长的独立论述才补来源。
- 一句转述之后紧接数句分析时，将注号放在转述句末，避免暗示后续分析是来源的原话。
- 不在术语、书名或人名中间插注；不连续堆多个上标。同一论断需要多个来源时，在一条注释里分别说明用途。
- 同一材料的同一场景可以复用同一个注释 ID；出现处各有独立返回锚点。不要为减少编号，把同一长篇资料中互不相邻的场景全塞进一条注释。
- 不规定每千字几个注号。优先去除重复的出处展示，不能为了正文清爽而删除必要依据。

### 5.3 原文与延伸阅读

Blue Note 回应在正文首次实质性点名原文时，可将篇名直接做成链接；底部保留模板生成的“Blue Note · 原文”入口。不要在每段转述后反复加 `(Cheology)`，也不要手写第三个同义导航块。

直接参与论证的材料必须在对应位置落注。“延伸阅读”只放供继续探索或比较的材料，写明作者、篇名及相关性。若实际借用了其观点，仍需在借用处引注；不能只放进延伸阅读来掩盖依赖。

## 6. 注释内容与来源选择

注释应回答三个问题：这是什么材料，具体在哪里，支持了正文的哪部分。

- 首次引用提供实际可确认的作者/机构、作品或文章名称、可定位章节与链接。出版年、版本、日期仅在确有信息且有必要时填写，不补猜测值。
- 后续注释可以简写作品名，但仍保留可直接访问的链接与场景/章节。优先使用源站已有且验证过的锚点；没有锚点就写清场景、章节或检索位置，不编造锚点、页码和时间戳。
- 链接文字使用作品名、章节名或内容描述。正文及注释都避免裸 URL、纯域名和“点击这里”。保留原文路径和必要定位参数，去掉无关追踪参数。
- 优先原作、官方发布与一手资料。非官方脚本、转录、玩家评论可以按用途采用，但首次说明其性质；玩家解读不能冒充创作者定论。
- 同一来源第一次出现时说明共同限制，后续不机械重复。涉及个人经历的限制如“未亲自游玩”只能依据实际记录，不能由 agent 推断。
- 事实转述和本文推论容易混淆时，注释可以简要说明边界。不要每条重复一段免责声明，也不要将本该留在正文的核心论证搬去注释。
- 默认保持一条注释一段。确需两段时使用四空格缩进。注释不是资料仓库，避免复制大段原文、截图、复杂表格或嵌套注释。
- 新增、替换链接应实际访问并检查内容。已有链接本次遇到 403、限流等问题，不等于原引用失效；记录访问限制，不伪称已重新核验，不随意换成没有核对过的来源。

## 7. Markdown 写法与生成约定

使用标准脚注写法。ID 是稳定的、语义化的小写英文名称，可用连字符；不是显示编号。编号由构建器按正文首次出现顺序生成。

```md
Asya 阅读童话，并将女孩得到奖赏解释为爱世界的结果。[^morozko]

这里开始本文自己的分析。

[^morozko]: 《Z.A.T.O. script dump》，[第二章第四日](https://dayli.ly/zato-script/#ep2d4)的图书馆场景。这里转述游戏中的阅读过程；随后关于“考试”的说法为本文解读。

## 延伸阅读

作者，[相关作品的标题](https://example.org/article/)。简述供对照阅读的理由。
```

- 定义集中放在主体论述之后，便于编辑。`## 延伸阅读` 是可选保留标题；构建器确保它位于生成的注释之后。不要手写 `## 注释`、编号列表、`<sup>` 或返回箭头模拟脚注。
- 重复引用写同一个 `[^morozko]`；不同场景用新的语义 ID。禁止数字 ID、空定义、重复定义、未使用定义和注释内嵌套注号。
- 需要演示 `[^example]` 字面语法时放入行内代码或 fenced code，避免被当成缺失注释。
- 保留已发布 ID，方便既有带片段地址继续访问。重排正文时只自动改变可见编号，不随手重命名 ID。
- `scripts/markdown.mjs` 使用锁定版本的 `marked`、`marked-footnote` 与 `katex` 在构建时渲染；每篇独立编号。浏览器不请求 Markdown 解析器。
- `scripts/writing.mjs` 负责元数据与外层页面；`templates/writing.html` 负责公共页面壳；单篇 Markdown 不复制这些部分。

## 8. 注释交互与可访问性

- 基础体验是普通 HTML 锚点：注号跳到文末，返回箭头跳到对应正文注号。无 JavaScript、触屏和键盘都必须可用。
- 注号在阅读时低调，但点击范围至少 24×24px；返回入口至少 28×28px。不得用绝对定位的大范围透明点击层覆盖相邻正文或其他链接。
- 每个注号有“注释 N”的可访问名称；返回链接说明编号和第几处引用。重复引用必须各自返回原位置，不把所有箭头指向第一次出现处。
- 键盘焦点清晰可见。注释目标可接收焦点，跳转后有细线提示和顶部留白；返回的正文注号也有目标提示。不可只靠颜色告诉用户位置。
- 行内上标不增大正文行距；正文句内不得显示方括号、站点标签或脚注卡片。注释区保持可读字号，不通过缩成小字来节省篇幅。
- 注释、来源和延伸阅读默认同页/同标签操作；不强制打开新窗口。默认不折叠文末注释。
- 当前不启用悬浮预览、侧栏注释、弹窗或滚动动画。未来若增加预览，只能作为增强：保留原锚点、触屏操作和键盘入口，并独立验收遮挡、焦点与窄屏行为。

## 9. 验证与发布

编辑 agent 应按下列顺序完成工作，不用“看起来正确”代替检查：

1. 读本规范、全站设计规范、文章元数据与全文；确认本次授权范围。
2. 先梳理正文论断与来源的对应关系，再调整注号。纯排版改版应比较去除引用标记后的正文，确认没有丢段、改写或改顺序。
3. 检查来源名称、定位、直接引用与转述的区别；单独记录访问受限或尚未核实的情况。
4. 运行 `npm run check`。现有检查覆盖脚注顺序、重复引用回链、文章间编号隔离、无脚本 HTML、缺失/重复/空/未使用/嵌套注释、正文重复 H1、页面重复 ID、本地资源与片段链接。
5. 在 `/ai-lab/` 前缀下检查首页、文字目录、已发布文章及一篇待写页。核对原标题地址、H1、日期、署名与原文往返。
6. 阅读页检查 1280px、390px、320px，明暗主题；正文、注释、延伸阅读无页面横向溢出。检查注号所在行的行高、长链接换行和浏览器缩放。
7. 实际点击首个注号、至少一个中段注号、重复引用及其各自返回箭头；键盘 Tab/Enter 检查。无脚本访问也应完成同样往返。变更阅读样式时检查 Chromium 与 WebKit。
8. 核对文件差异；有新增规范时同步所有入口。禁止把 `docs/`、测试、源码、原始 Markdown 或元数据直接复制进部署目录。
9. 按已授权的发布流程提交、推送 `main`，等待该提交的 Actions 成功，再检查线上页面与本次构建一致。用户要求本地或草稿时遵循该要求。

自动检查只能判断格式、锚点与结构，不能证明文献可靠或解释正确。视觉验收与来源核对的结论应如实区分，不把一个通过的构建说成所有语义都已核验。
